# Codex 到底是什么

## 这一章要解决什么问题

很多新手把 Codex 当成“会聊天的搜索框”，于是只会问问题，不会交付任务。更准确的理解是：**Codex 是一个可以读取上下文、调用工具、修改文件、运行验证并根据结果继续迭代的工作伙伴**。

它通常由五层组成：

| 层 | 用大白话理解 | 例子 |
| --- | --- | --- |
| 目标 | 你想得到什么结果 | 做一个个人记账页面 |
| 上下文 | 它需要知道什么 | 现有代码、图片、表格、规则 |
| 工具 | 它可以做什么 | 读文件、运行命令、打开浏览器 |
| 工作流 | 它按什么步骤完成 | 先检查、再修改、再测试 |
| 验收 | 你怎么判断完成 | 页面能打开，测试通过，文件位置正确 |

## Codex 不是自动负责制

Codex 可以替你执行很多步骤，但目标、边界和最终责任仍然属于你。尤其要记住：

- 它能生成代码，不代表代码一定适合你的业务。
- 它能读取资料，不代表资料中的结论已经核实。
- 它能操作电脑，不代表每一步都应该自动执行。
- 它能完成一大段任务，不代表你不需要设置检查点。
- 它能给出看起来合理的结果，不代表结果已经通过测试。

把 Codex 当作一位速度很快、需要明确上下文、必须接受验收的执行者，通常比把它当作“万能专家”更可靠。

## 第一个最小任务

新建一个空文件夹，例如 `codexstart-practice`，然后对 Codex 说：

```text
请先查看当前目录，不要修改任何文件。
告诉我：
1. 当前有哪些文件；
2. 你认为这个目录适合做什么练习；
3. 如果要创建一个个人工作台，还缺哪些信息。
最后只输出观察结果和待确认问题。
```

这个任务故意不让 Codex 立刻写代码。你要观察它是否会先了解环境、列出不确定性，并尊重“不要修改”的边界。

## 用四句话描述一次任务

之后每次提问，都尽量包含四个部分：

1. **目标**：最后要得到什么。
2. **范围**：允许读写哪些文件、使用哪些工具。
3. **标准**：什么情况才算完成。
4. **限制**：哪些动作不能做，哪些决定必须先问你。

例如：

```text
目标：在当前目录做一个可打开的个人任务看板。
范围：只新增 index.html、styles.css 和 app.js，不改其他文件。
标准：可以新增、完成、筛选任务，刷新页面后数据仍然保留。
限制：不要引入构建工具，不要联网，不要删除现有文件。
完成前先给出计划，完成后运行一个最小检查并说明结果。
```

## 课后任务

把你最近想做的一件小事改写成“目标、范围、标准、限制”四句话。不要追求复杂，先让另一个人只看这四句话就能开始工作。
