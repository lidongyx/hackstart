# 用 Expo 构建 React Native 应用

从移动应用想法到可运行 Expo 原型，包含导航、状态、样式和本地预览。

## 场景定位

这个案例属于“移动与桌面原生开发”。它适合把一个经常需要人工整理、判断或验证的流程交给 Codex 做第一轮处理，然后由你审阅关键结果。

| 项目 | 内容 |
| --- | --- |
| 适合任务 | 从移动应用想法到可运行 Expo 原型，包含导航、状态、样式和本地预览。 |
| 常用能力 | React Native、Expo、跨端移动 |
| 产出形态 | 清单、草稿、补丁、报告、截图、表格或可运行原型，取决于具体任务 |

## 适合谁

- 想快速做跨平台 App 原型
- 需要标准 Expo 项目结构
- 希望在手机或模拟器预览

## Codex 可以帮你做什么

- 初始化 Expo 项目
- 实现导航和页面状态
- 加入基础样式和数据
- 说明预览和构建命令

## 推荐工作流

1. 先确定核心页面和用户动作
2. 使用 Expo 常规结构
3. 先用本地数据
4. 验证 iOS 和 Android 预览
5. 后续再接原生权限和发布

## 示例提示词

```text
请用 Expo 创建一个 React Native 应用原型。包含首页、列表、详情和设置页。使用 Expo 常规项目结构，并告诉我如何在本地预览。
```

## 案例重点展开

- 先使用 Expo Go 和 Expo Router，快速验证移动端原型。
- 可以接入 Expo 插件或 MCP server 辅助项目创建和调试。
- 验证路径优先选择最快的：真机 Expo Go 或模拟器。
- 提示词里写清目标平台、页面、导航和约束。
- 原生权限、发布和商店配置后续再拆开处理。

## 完整用法拆解

### 1. 先把任务范围说清楚

这个案例的重点不是让 Codex 猜你的真实需求，而是把“从移动应用想法到可运行 Expo 原型，包含导航、状态、样式和本地预览。”拆成一组可以检查的步骤。开始时先说明输入来源、时间范围、目标对象和最终产物。如果任务涉及多个工具，也要告诉 Codex 哪些工具可以读、哪些动作只能准备草稿。

可以把范围写成三句话：我要处理什么资料、希望得到什么结果、哪些事情不能自动执行。对于“移动与桌面原生开发”这类任务，范围越清楚，Codex 越容易把注意力放在真正有价值的判断上。

### 2. 让 Codex 先输出中间结果

不要一上来要求最终答案。更稳妥的方式是先让 Codex 完成“初始化 Expo 项目”，再让它解释判断依据。这样你可以在中间阶段纠偏，避免它把不重要的信息写进最终产物。

如果任务比较长，可以要求 Codex 先给你一个小型样例，例如前 5 条记录、前 3 个页面、一个模块或一封邮件。样例通过后，再扩大到完整范围。

### 3. 把工具和证据写进交付物

这个场景常用能力包括：React Native、Expo、跨端移动。让 Codex 使用这些能力时，最好要求它把依据也写出来：读了哪些文件、参考了哪些消息、运行了哪些命令、看到哪些截图或日志。

证据不是为了增加篇幅，而是为了让你能判断结果是否可靠。特别是 想快速做跨平台 App 原型，更应该看到来源、假设和未确认问题。

### 4. 逐轮校准，而不是一次到位

第一次结果通常是校准样本。你可以告诉 Codex 哪些判断正确、哪些内容太泛、哪些边界必须更严格。经过几轮之后，再考虑把流程保存为技能、自动化或长期 goal。

一个可用的校准顺序是：先确定核心页面和用户动作；使用 Expo 常规结构；最后 后续再接原生权限和发布。这样既能提高产出质量，也能减少误操作。

## 交付物检查清单

完成这类任务后，建议检查以下内容：

- 是否清楚说明了输入来源、处理范围和时间范围。
- 是否把“初始化 Expo 项目”和“实现导航和页面状态”的依据写出来。
- 是否列出了不确定信息、缺失材料和需要你确认的问题。
- 是否避免了越权动作，尤其是发送、删除、付款、发布、承诺和修改生产数据。
- 是否留下了下一步可以继续执行的清单、文件、补丁、报告或验证结果。

## 使用边界

- 原生权限不要混在第一版
- iOS 和 Android 差异要检查
- Expo 发布流程需要单独配置
