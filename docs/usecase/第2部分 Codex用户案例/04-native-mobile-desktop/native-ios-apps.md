# 构建 iOS 应用

让 Codex 搭建、构建和调试 SwiftUI iPhone / iPad 应用。

## 场景定位

这个案例属于“移动与桌面原生开发”。它适合把一个经常需要人工整理、判断或验证的流程交给 Codex 做第一轮处理，然后由你审阅关键结果。

| 项目 | 内容 |
| --- | --- |
| 适合任务 | 让 Codex 搭建、构建和调试 SwiftUI iPhone / iPad 应用。 |
| 常用能力 | iOS、SwiftUI、Simulator |
| 产出形态 | 清单、草稿、补丁、报告、截图、表格或可运行原型，取决于具体任务 |

## 适合谁

- 需要 iOS 原型
- 想学习 SwiftUI 应用结构
- 要在模拟器中验证流程

## Codex 可以帮你做什么

- 搭建项目结构
- 实现导航、列表、详情和表单
- 处理本地状态
- 构建并在模拟器检查

## 推荐工作流

1. 指定设备和 iOS 版本
2. 先实现核心用户路径
3. 用模拟数据验证界面
4. 跑构建和模拟器
5. 记录无法验证的原生能力

## 示例提示词

```text
请创建一个 SwiftUI iOS 应用原型。包含列表、详情、编辑表单和本地状态。用 Xcode 构建并在模拟器验证主要流程。
```

## 案例重点展开

- 新 iOS 应用先建立 scaffold 和构建循环。
- 尽量保持 CLI-first，通过构建命令和模拟器验证，而不是只依赖 Xcode UI。
- 可以使用 iOS 相关技能处理 SwiftUI、性能、并发、Liquid Glass 和视图重构。
- 每轮都应构建或运行，及时发现工具链问题。
- 交付物包括可运行项目、验证结果和下一步建议。

## 完整用法拆解

### 1. 先把任务范围说清楚

这个案例的重点不是让 Codex 猜你的真实需求，而是把“让 Codex 搭建、构建和调试 SwiftUI iPhone / iPad 应用。”拆成一组可以检查的步骤。开始时先说明输入来源、时间范围、目标对象和最终产物。如果任务涉及多个工具，也要告诉 Codex 哪些工具可以读、哪些动作只能准备草稿。

可以把范围写成三句话：我要处理什么资料、希望得到什么结果、哪些事情不能自动执行。对于“移动与桌面原生开发”这类任务，范围越清楚，Codex 越容易把注意力放在真正有价值的判断上。

### 2. 让 Codex 先输出中间结果

不要一上来要求最终答案。更稳妥的方式是先让 Codex 完成“搭建项目结构”，再让它解释判断依据。这样你可以在中间阶段纠偏，避免它把不重要的信息写进最终产物。

如果任务比较长，可以要求 Codex 先给你一个小型样例，例如前 5 条记录、前 3 个页面、一个模块或一封邮件。样例通过后，再扩大到完整范围。

### 3. 把工具和证据写进交付物

这个场景常用能力包括：iOS、SwiftUI、Simulator。让 Codex 使用这些能力时，最好要求它把依据也写出来：读了哪些文件、参考了哪些消息、运行了哪些命令、看到哪些截图或日志。

证据不是为了增加篇幅，而是为了让你能判断结果是否可靠。特别是 需要 iOS 原型，更应该看到来源、假设和未确认问题。

### 4. 逐轮校准，而不是一次到位

第一次结果通常是校准样本。你可以告诉 Codex 哪些判断正确、哪些内容太泛、哪些边界必须更严格。经过几轮之后，再考虑把流程保存为技能、自动化或长期 goal。

一个可用的校准顺序是：指定设备和 iOS 版本；先实现核心用户路径；最后 记录无法验证的原生能力。这样既能提高产出质量，也能减少误操作。

## 交付物检查清单

完成这类任务后，建议检查以下内容：

- 是否清楚说明了输入来源、处理范围和时间范围。
- 是否把“搭建项目结构”和“实现导航、列表、详情和表单”的依据写出来。
- 是否列出了不确定信息、缺失材料和需要你确认的问题。
- 是否避免了越权动作，尤其是发送、删除、付款、发布、承诺和修改生产数据。
- 是否留下了下一步可以继续执行的清单、文件、补丁、报告或验证结果。

## 使用边界

- 设备尺寸和 iPad 布局要单独看
- 权限、推送和后端不应混在第一步
- 模拟器通过不代表真机完全一致
