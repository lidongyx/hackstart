# 迁移到 Liquid Glass

把现有 SwiftUI 应用迁移到 iOS 26 / Xcode 26 的 Liquid Glass 风格 API。

## 场景定位

这个案例属于“移动与桌面原生开发”。它适合把一个经常需要人工整理、判断或验证的流程交给 Codex 做第一轮处理，然后由你审阅关键结果。

| 项目 | 内容 |
| --- | --- |
| 适合任务 | 把现有 SwiftUI 应用迁移到 iOS 26 / Xcode 26 的 Liquid Glass 风格 API。 |
| 常用能力 | iOS 26、Xcode 26、SwiftUI 新 API |
| 产出形态 | 清单、草稿、补丁、报告、截图、表格或可运行原型，取决于具体任务 |

## 适合谁

- 已有 SwiftUI 应用要跟进新视觉风格
- 需要评估迁移范围
- 希望保留原有信息架构

## Codex 可以帮你做什么

- 扫描可迁移组件
- 替换必要 API
- 控制最低系统版本
- 运行新工具链构建

## 推荐工作流

1. 先确认 Xcode 和系统版本
2. 只迁移关键界面
3. 保留旧系统兼容策略
4. 截图比较迁移前后
5. 记录无法迁移的组件

## 示例提示词

```text
请评估这个 SwiftUI 应用迁移到 Liquid Glass 的范围。只修改必要视图，保留原有信息架构。完成后用 Xcode 26 构建，并说明最低系统版本。
```

## 案例重点展开

- 从 iOS 26 和 Xcode 26 基线开始，先确认工具链可用。
- 优先使用原生 API，例如 glass effect 和相关容器，而不是手写仿制效果。
- 先让 Codex 做迁移计划，再选择一个页面或组件切片实施。
- 参考 WWDC 新设计系统和 SwiftUI 更新，避免过时用法。
- 每次迁移都要构建并视觉检查。

## 完整用法拆解

### 1. 先把任务范围说清楚

这个案例的重点不是让 Codex 猜你的真实需求，而是把“把现有 SwiftUI 应用迁移到 iOS 26 / Xcode 26 的 Liquid Glass 风格 API。”拆成一组可以检查的步骤。开始时先说明输入来源、时间范围、目标对象和最终产物。如果任务涉及多个工具，也要告诉 Codex 哪些工具可以读、哪些动作只能准备草稿。

可以把范围写成三句话：我要处理什么资料、希望得到什么结果、哪些事情不能自动执行。对于“移动与桌面原生开发”这类任务，范围越清楚，Codex 越容易把注意力放在真正有价值的判断上。

### 2. 让 Codex 先输出中间结果

不要一上来要求最终答案。更稳妥的方式是先让 Codex 完成“扫描可迁移组件”，再让它解释判断依据。这样你可以在中间阶段纠偏，避免它把不重要的信息写进最终产物。

如果任务比较长，可以要求 Codex 先给你一个小型样例，例如前 5 条记录、前 3 个页面、一个模块或一封邮件。样例通过后，再扩大到完整范围。

### 3. 把工具和证据写进交付物

这个场景常用能力包括：iOS 26、Xcode 26、SwiftUI 新 API。让 Codex 使用这些能力时，最好要求它把依据也写出来：读了哪些文件、参考了哪些消息、运行了哪些命令、看到哪些截图或日志。

证据不是为了增加篇幅，而是为了让你能判断结果是否可靠。特别是 已有 SwiftUI 应用要跟进新视觉风格，更应该看到来源、假设和未确认问题。

### 4. 逐轮校准，而不是一次到位

第一次结果通常是校准样本。你可以告诉 Codex 哪些判断正确、哪些内容太泛、哪些边界必须更严格。经过几轮之后，再考虑把流程保存为技能、自动化或长期 goal。

一个可用的校准顺序是：先确认 Xcode 和系统版本；只迁移关键界面；最后 记录无法迁移的组件。这样既能提高产出质量，也能减少误操作。

## 交付物检查清单

完成这类任务后，建议检查以下内容：

- 是否清楚说明了输入来源、处理范围和时间范围。
- 是否把“扫描可迁移组件”和“替换必要 API”的依据写出来。
- 是否列出了不确定信息、缺失材料和需要你确认的问题。
- 是否避免了越权动作，尤其是发送、删除、付款、发布、承诺和修改生产数据。
- 是否留下了下一步可以继续执行的清单、文件、补丁、报告或验证结果。

## 使用边界

- 新 API 变化快，要以当前工具链为准
- 不要为了视觉升级破坏可用性
- 兼容路径需要明确
