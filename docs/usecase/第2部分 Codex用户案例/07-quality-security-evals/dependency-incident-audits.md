# 审计依赖事故

根据公开依赖安全公告检查仓库是否受影响，形成审计和缓解计划。

## 场景定位

这个案例属于“质量、安全与评估”。它适合把一个经常需要人工整理、判断或验证的流程交给 Codex 做第一轮处理，然后由你审阅关键结果。

| 项目 | 内容 |
| --- | --- |
| 适合任务 | 根据公开依赖安全公告检查仓库是否受影响，形成审计和缓解计划。 |
| 常用能力 | 依赖安全、供应链、事故响应 |
| 产出形态 | 清单、草稿、补丁、报告、截图、表格或可运行原型，取决于具体任务 |

## 适合谁

- 某个公共包出现安全公告
- 不确定项目是否受影响
- 需要快速给团队风险判断

## Codex 可以帮你做什么

- 检查依赖版本和锁文件
- 追踪是否存在可利用调用路径
- 评估暴露面
- 提出升级或缓解方案

## 推荐工作流

1. 先输入公告摘要和受影响版本
2. 扫描直接和间接依赖
3. 区分存在依赖和可利用路径
4. 保持只读输出审计计划
5. 确认后再升级修复

## 示例提示词

```text
请根据这个公开依赖安全公告审计当前仓库。先判断是否使用受影响版本，再检查调用路径、暴露面、缓解措施和升级方案。保持只读，先输出审计计划和证据。
```

## 案例重点展开

- 第一步先安全地总结公告：影响版本、攻击条件和建议缓解。
- 保持首轮只读，检查依赖树、锁文件和调用路径。
- 报告中把 confirmed exposure、needs verification 和 ruled out 分开。
- 每个发现都要有证据状态、严重性和下一步。
- 需要修复时再进入安全修复 backlog。

## 完整用法拆解

### 1. 先把任务范围说清楚

这个案例的重点不是让 Codex 猜你的真实需求，而是把“根据公开依赖安全公告检查仓库是否受影响，形成审计和缓解计划。”拆成一组可以检查的步骤。开始时先说明输入来源、时间范围、目标对象和最终产物。如果任务涉及多个工具，也要告诉 Codex 哪些工具可以读、哪些动作只能准备草稿。

可以把范围写成三句话：我要处理什么资料、希望得到什么结果、哪些事情不能自动执行。对于“质量、安全与评估”这类任务，范围越清楚，Codex 越容易把注意力放在真正有价值的判断上。

### 2. 让 Codex 先输出中间结果

不要一上来要求最终答案。更稳妥的方式是先让 Codex 完成“检查依赖版本和锁文件”，再让它解释判断依据。这样你可以在中间阶段纠偏，避免它把不重要的信息写进最终产物。

如果任务比较长，可以要求 Codex 先给你一个小型样例，例如前 5 条记录、前 3 个页面、一个模块或一封邮件。样例通过后，再扩大到完整范围。

### 3. 把工具和证据写进交付物

这个场景常用能力包括：依赖安全、供应链、事故响应。让 Codex 使用这些能力时，最好要求它把依据也写出来：读了哪些文件、参考了哪些消息、运行了哪些命令、看到哪些截图或日志。

证据不是为了增加篇幅，而是为了让你能判断结果是否可靠。特别是 某个公共包出现安全公告，更应该看到来源、假设和未确认问题。

### 4. 逐轮校准，而不是一次到位

第一次结果通常是校准样本。你可以告诉 Codex 哪些判断正确、哪些内容太泛、哪些边界必须更严格。经过几轮之后，再考虑把流程保存为技能、自动化或长期 goal。

一个可用的校准顺序是：先输入公告摘要和受影响版本；扫描直接和间接依赖；最后 确认后再升级修复。这样既能提高产出质量，也能减少误操作。

## 交付物检查清单

完成这类任务后，建议检查以下内容：

- 是否清楚说明了输入来源、处理范围和时间范围。
- 是否把“检查依赖版本和锁文件”和“追踪是否存在可利用调用路径”的依据写出来。
- 是否列出了不确定信息、缺失材料和需要你确认的问题。
- 是否避免了越权动作，尤其是发送、删除、付款、发布、承诺和修改生产数据。
- 是否留下了下一步可以继续执行的清单、文件、补丁、报告或验证结果。

## 使用边界

- 不能只看版本号下结论
- 供应链事故需要快速但谨慎
- 升级可能引入兼容性风险
