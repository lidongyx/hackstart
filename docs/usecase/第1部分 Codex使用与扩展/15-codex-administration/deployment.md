# Deployment 部署管理

Codex 的部署管理不是单一按钮，而是一组工作流选择：本地交互、Codex Cloud、Sites、CI、GitHub Action、远程主机和企业托管配置都可能参与上线链路。

## 官方内容整理

- Codex 本地模式适合在开发者电脑或远程开发机上完成代码修改、测试、文档和发布准备。
- Codex Cloud 适合在托管环境中并行处理任务，尤其是 GitHub 仓库相关的实现、修复和评审。
- Sites 可以把提示词或兼容项目变成托管站点，适合网站、Web App、小游戏和可预览产物。
- GitHub Action 可以在 CI/CD 中运行 Codex，生成评审、补丁、发布说明或自动修复建议。
- 非交互模式 `codex exec` 适合脚本化任务，能输出 JSONL 事件流、保存最终消息，并用结构化 schema 约束输出。
- App Server 和 SDK 更适合产品级集成：把 Codex 嵌入你自己的工具、面板、后台任务系统或内部研发平台。
- 企业部署还需要考虑认证方式、访问令牌、RBAC、managed configuration、治理报表和合规日志。
- 远程连接适合把 Codex App 接到 SSH 主机或常开机器，从而在远程环境里执行项目任务。

## 实践补充

部署策略最好按“谁来触发、在哪里运行、谁来确认、如何回滚”来设计。个人项目可以让 Codex 直接帮你构建和部署；团队项目应把 Codex 放在 PR、CI、预览环境和人工审批之间，而不是让它绕过现有发布制度。

对于中文用户推广，建议把 Codex 解释为“能参与部署流程的工程助手”，而不是“自动上线机器人”。它可以生成配置、修复构建、检查日志、写发布说明、打开 PR，但生产发布仍应经过团队已有的权限与审计流程。

## 推荐工作流

1. 把部署链路分为准备、构建、验证、发布、回滚五段。
2. 让 Codex 先负责准备、验证和报告，再逐步进入自动修复和 PR 创建。
3. 所有生产发布动作都通过 CI、平台权限和人工确认承载。
4. 为每个环境写清楚 Codex 能读取什么、能写什么、能否联网、能否调用外部工具。
5. 让 Codex 每次部署前输出变更摘要、验证结果、风险点和回滚命令。

## 示例提示词

```text
请把这个项目的发布流程整理成 Codex 可执行的部署手册。分为准备、构建、测试、预览、生产发布、回滚六部分，并标出哪些步骤可以自动执行、哪些步骤必须人工确认。
```

```text
请检查本次发布前的风险。读取 Git diff、CI 配置、部署脚本和环境变量示例文件，输出阻塞项、建议修复、验证命令和发布后观察指标。
```
